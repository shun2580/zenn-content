## 突然の3時間超ハング

ある朝、マルチエージェントシステムの1体（ashigaru7）が、3時間以上もハングしました。画面を覗くと、opencode の TUI は「処理中」のまま凍りついており、左上の経過時間は一切進まなくなっていました。当然、作業は全く進みません。

この記事では、その時の調査過程と、そこから得た教訓をまとめます。

## 背景：コスト削減でローカルLLMに切り替えた

該当のエージェント（ashigaru7）は、コスト削減のためにローカルLLM（Ollama の `qwen3.5:9b`）を opencode 経由で動かしていました。一度はうまく動いていたのですが、ある日突然このハングが起きました。

ちなみに、このマルチエージェントシステム自体の詳しい説明は別記事（「監視スクリプトがローカルLLMを無応答と誤判定してTUIをsetRawMode errno5でクラッシュさせた話」・未公開）に譲ります。そちらではローカルLLMの遅さに監視スクリプトが誤反応して TUI を落とす事象をまとめていますが、今回の話はむしろその後の教訓です。

## 一次対応：「タイムアウトを設定すればいいだろう」

調査チーム（以降「軍師」）が opencode の設定ファイル（`opencode.jsonc`）を確認すると、このローカルLLM用には特にタイムアウトが設定されていませんでした。

そこで、単純な対応を入れました。
```jsonc
{
  "provider": {
    "ollama": {
      "options": {
        "chunkTimeout": 30000,
        "timeout": 60000
      }
    }
  }
}
```

設定を反映させて再起動したのですが……**翌日、同じハングが再発した**。タイムアウト設定を入れたのに、なぜ？

## 隔離環境での再現：「設定は正しく機能している」

ここで謎が深まります。軍師は、opencode の隔離テスト環境（他のエージェントに一切影響しない条件下）で、同じモデル・同じ設定でテストしてみました。

```bash
timeout 90 opencode run "say hi in one word" \
  --model ollama/qwen3.5:9b \
  --print-logs --log-level DEBUG
```

結果は、**設定自体は完全に正しく機能していました**。

```
09:13:36.184 stream providerID=ollama modelID=qwen3.5:9b ...
（60.013秒後）
09:14:36.197 ERROR stream error ... error.error="TimeoutError: The operation timed out."
09:14:36.204 ERROR process ... error="The operation timed out."
```

タイムスタンプを見ると、ちょうど **60.013秒後に「TimeoutError」が発火して、正常に終了しています**。プロセスはハングせず、exit code 1 で異常終了（正常な終了形式）。

つまり：
- **実測値: 60013ms でタイムアウト発動確認**
- エラーメッセージ: クリーンに「The operation timed out」
- プロセス: ハングなし、正常に終了

「設定を入れた」という事実だけでは、「その設定が実際に効く経路を通っている」ことを保証しない——これが最大の教訓でした。

## しかし、対話TUIモードでは同じ保護が効いていない

隔離テスト（`opencode run` 単体モード）では完璧に機能するタイムアウト。では、なぜ実運用の対話TUIモード（ashigaru7 が実際に使っている稼働形態）では 3 時間もハングしたのか？

軍師の判断では、**最も有力な推論は、opencode の対話TUIモード内部に、設定されたタイムアウトエラーを正しく検知・表示・回復できないエラーハンドリング不備が存在する、ということです**（仮説）。

つまり：
- **内部的には** opencode.jsonc の timeout 設定は正しく機能している（隔離テストで確認）
- しかし**対話TUIモード** は、その内部エラーを画面に反映できず、既にネットワークレベルでは終わった処理を「処理中」のままフリーズして表示し続ける
- その結果、ユーザーから見ると「ハング」に見える

ただし、本タスクでは隔離約束（live agent への干渉厳禁）の制約上、対話TUIモード自体を直接再現・観測することはできていません。**この最終段階の結論は、証拠に基づく強い推論であり、100%の直接観測による確定ではありません**。記事ではこの不確実性を明確に記載しています。

## 副産物の発見：Ollama の OpenAI 互換 API は冷たい

調査の過程で、思わぬ発見もありました。Ollama のコールド状態（モデル未ロード）での振る舞いです。

軍師が `curl` で直接テストしてみたところ：

**OpenAI 互換エンドポイント（`/v1/chat/completions`）:**
- 1回目: `timeout 30` → 30秒間、HTTP応答ヘッダすら一切受信されず
- 2回目: `timeout 100` → 100秒間、やはり無応答
- この間、`ollama ps` はモデル未ロード状態が継続

**ネイティブエンドポイント（`/api/chat`）:**
- 同一モデル・同一プロンプトで約 **20 秒で完走**
  - ロード時間: 約 13.6 秒
  - 実生成: 残り約 6 秒
- 正常なストリーミング応答（実際の会話文）を返す

**同じサーバー・同じモデルなのに、OpenAI互換エンドポイントは 130秒超の無応答、ネイティブは 20秒で完走**という、顕著な非対称が実測されました。

opencode は内部で `@ai-sdk/openai-compatible` ドライバを使っており（ログの `llm.runtime=ai-sdk` で確認）、このエンドポイント側の挙動特性の影響を直接受けることになります。

## モデル側の制約も判明

さらに詳しく見ると、使っていたモデル（`qwen3.5:9b`）の実ロードサイズは **8.8GB** であるのに対し、GPU VRAM は **8GB** しかありません。

結果として、メモリ配置は：
- GPU: 72%（メモリ使用）
- CPU: 28%（メモリ使用）

という、**CPU と GPU にまたがる分割稼働** になっていました。

実際のタスク（system prompt や tool 定義を含む大きなプロンプト）を扱うとなれば、このメモリ制約下でのプロンプト評価に時間がかかり、**60秒のタイムアウト閾値に到達する確率が、単純な「hi」というプロンプトより格段に高い** と考えられます。

## 対応：すべて Claude に統一

こうした調査を踏まえて、最終的な対応は **「Ollama は休眠温存し、全エージェントを Claude に統一」** というものになりました。

ローカルLLM はコスト削減の魅力がありますが、その「遅さ」という性質は、周囲のインフラ（タイムアウト・エラーハンドリング・TUI実装）の前提をこっそり崩していきます。今回もまた、見た目は「ハング」という単純な不具合に見えながら、ほどいてみれば「設定と実装パス の乖離」「外部依存（ollama API）の非対称性」「メモリ制約下での遅延」という、複数の層が絡んだ問題でした。

## まとめ：「入れた」と「効く」は別問題

最大の教訓は、これです：

> 「タイムアウトを設定した」ことと「その設定が実際に効く経路を通っている」ことは、別の問題である

隔離テストでタイムアウトが正しく発動することを確認しても、実運用環境のすべての経路でそれが機能することを保証しません。特に opencode のような多層構造のツール（CLI ブリッジ → TUI ループ → LLM ドライバ → 外部 API）では、どの層でも「設定を読み込んだが、その効果を活かしきれていない」という齟齬が起きる可能性があります。

今回、最も疑わしいのは **opencode**（ブリッジ CLI）です。ただし、TUI 層のエラーハンドリング不備が根本原因という結論は、隔離環境での直接観測ではなく状況証拠に基づく推論です。少なくとも、Ollama が遅かったわけでも、ローカルLLM がダメだったわけでもないことは実測で確認できています。
