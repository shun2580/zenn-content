## 突然の3時間超ハング

ある日の昼過ぎのことです。マルチエージェントシステムの1体（足軽7）が、起動から3時間以上ハングしたままになっているのに気づきました。画面を覗くと、opencode の TUI は「処理中」のまま凍りついており、左上の経過時間は一切進まなくなっていました。当然、作業は全く進みません。

この記事では、その時の調査過程と、そこから得た教訓をまとめます。

## 背景：コスト削減でローカルLLMに切り替えた

筆者は、Claude Code などの CLI エージェントを複数並列で動かすマルチエージェント環境（[multi-agent-shogun](https://zenn.dev/shio_shoppaize/articles/5fee11d03a11a1) を自分用にカスタマイズしたもの）で開発をしています。エージェントには役割ごとに名前が付いており、本記事では実行担当のワーカーを「足軽」、タスク管理役を「家老」、調査・品質チェック担当を「軍師」と呼びます。

今回ハングしたローカルLLM担当の役割は、6月中旬から3週間ほど、足軽4が（自動復旧を挟みつつ）担っていたものです。本件のような凍結型ハング（TUIが生きたまま固まる）の記録はありません。一方、TUIの予期せぬ終了（クラッシュしてシェルに落ちる）は別事象として過去に発生しており（2日間で計4回、監視側の自動復旧で回復）、これは別記事で扱った事象です。なお、クラッシュはエージェントの画面（tmux のペイン）がシェルに落ちるため監視側が自動検知・復旧できますが、凍結はプロセスが生きたままのため死活判定をすり抜けます。今回のハングが3時間以上検知されなかった一因はここにあります。

足軽7がこの役割を引き継いだのは、まさにハングが起きた当日です。コスト削減のため、ローカルLLM（Ollama の `qwen3.5:9b`）を opencode 経由で動かす構成をそのまま受け継ぎました。冒頭のハングは、配備初日の最初のタスク（疎通確認）が完了しないまま起きたものです。

本記事では記事の本筋（タイムアウト設定とハングの関連性）に絞っていますが、背景として、このマルチエージェントシステムでは監視スクリプトがローカルLLMの遅さを無応答と誤判定し、opencode の TUI を予期せず終了させるという別の事象も過去に報告されています。当記事はそうした経験の後、より深く調査した結果をまとめたものです。

## 一次対応：「タイムアウトを設定すればいいだろう」

軍師が opencode の設定ファイル（`opencode.jsonc`）を確認すると、このローカルLLM用には特にタイムアウトが設定されていませんでした。そこで軍師の診断を受け、足軽2が単純な対応を入れました。
```jsonc
{
  "provider": {
    "ollama": {
      "options": {
        "chunkTimeout": 30000,
        "timeout": 60000
      }
    }
  }
}
```

（注：上記はプロジェクトレベルの `opencode.jsonc` の抜粋です。opencode が起動時にグローバル設定（`~/.config/opencode/opencode.jsonc`）へ自動マージします。読み込まれるかどうかは起動時の作業ディレクトリに依存します。）

設定を反映して再起動したのですが……**その後も応答はなく、2時間半ほど経った夕方、同じハング状態に陥っていると判断しました**。TUI は相変わらず「処理中」のまま凍りつき、左上の経過時間は一切進まない。同じ足軽7で、同じ症状の繰り返しです。タイムアウト設定を入れたのに、なぜ？

## 隔離環境での再現：「設定は正しく機能している」

ここで謎が深まります。軍師は、opencode の隔離テスト環境（他のエージェントに一切影響しない条件下）で、同じモデル・同じ設定でテストしてみました。

```bash
timeout 90 opencode run "say hi in one word" \
  --model ollama/qwen3.5:9b \
  --print-logs --log-level DEBUG
```

結果は、タイムアウト設定の動作が実測で確認できました。

```
09:13:36.184 stream providerID=ollama modelID=qwen3.5:9b ...
（60.013秒後）
09:14:36.197 ERROR stream error ... error.error="TimeoutError: The operation timed out."
09:14:36.204 ERROR process ... error="The operation timed out."
```
（ログの時刻は UTC 表記です。日本時間だと 18時過ぎにあたります。）

タイムスタンプを見ると、ちょうど **60.013秒後に「TimeoutError」が発火して、正常に終了しています**。ハングやクラッシュではなく、エラーとして正しく終了しました（exit code 1）。

テスト時にモデルがロード済み（ウォーム）だったかどうかの記録は残していませんが、直前の curl テストでロード済みだったはずなので、おそらくウォームです（ログファイル名にも warm と付けていました）。実測で確認できたのは `timeout` の発火です。

つまり：
- **実測値: 60000ms（timeout設定値）での発火を確認**
- エラーメッセージ: クリーンに「The operation timed out」
- プロセス: ハングなし、正常に終了
- **補足: chunkTimeout（30秒）の発火は観測されていません**。opencode.exeバイナリの静的解析（strings検索）では、chunkTimeout の実装コード自体は見つかります。ただし、バイナリの minified コードから読み取れる限りでは、初回の fetch 応答が返ってきた後にのみ監視が開始される設計と解釈できます。この解釈は、隔離テストで 60秒（timeout）側が発火したという実測結果と整合します。

「設定を入れた」という事実だけでは、「その設定が実際に効く経路を通っている」ことを保証しない——これが最大の教訓でした。

## しかし、対話TUIモードでは同じ保護が効いていない

隔離テスト（`opencode run` 単体モード）では `timeout` の発火が実測で確認できたタイムアウト。では、なぜ実運用の対話TUIモード（足軽7が実際に使っている稼働形態）では 3 時間もハングしたのか？

軍師の判断では、**最も有力な推論は、問題が opencode の対話TUIモード側にある、ということです**。複数の仮説が考えられます：

**仮説A（TUIエラーハンドリング不備）**：内部的には opencode.jsonc の timeout 設定は正しく機能しているが、対話TUIモードはその内部エラーを画面に反映できず、(仮説Aが正しければ)内部的には終了しているはずの処理を「処理中」のままフリーズして表示し続ける。

**仮説B（設定適用漏れ）**：設定ファイルが読み込まれていない可能性。

調査チームが確認した結果：
- ハング当時の実プロセス（PID 18141）の `/proc/environ` から、家老が PWD を採取して確認
- 軍師が実施した隔離テスト（別プロセス）の DEBUG ログに「loading path」が現れた

この2つは、**別々の証拠**です。設定が読み込まれる条件（cwd の一致）はハング当時の実プロセスで確認できましたが、PID 18141 自身が実際に opencode.jsonc を読み込んだことを示す直接ログは、本調査では採取されていません。

したがって**仮説B は棄却できます**。

**仮説C（TUI経路でのタイムアウト不発）**：設定は読み込まれたものの、対話TUIモードの経路では timeout がそもそも発火していない可能性です。隔離テストが証明したのは `opencode run` 経路での発火のみで、TUI経路での発火は観測できていません。傍証があります。opencode.exeバイナリの静的解析（strings検索）により、chunkTimeout の実装コード自体は存在することを確認しましたが、コード断片から読み取れる限りでは、初回の fetch 応答が返ってきた後にのみ監視が開始される設計と解釈できます（バイナリの minified コードの断片的な解析であり、完全な制御フロー追跡ではありません）。この解釈は、隔離テストで 30秒（chunkTimeout）ではなく 60秒（timeout）側が発火したという実測結果と整合します。つまり「設定として受理されたキーが、経路や局面によっては部分的にしか効かない」実装が、opencode には現に存在します。timeout が TUI 経路で同様の状態にある可能性は、否定できません。

現時点の証拠では、**仮説Aと仮説Cは区別できません**。ただし、どちらであっても焦点は opencode 側の実装にあります。

本タスクでは隔離約束（live agent への干渉厳禁）の制約上、対話TUIモード自体を直接再現・観測することはできていません。**これらの仮説と傍証は、状況証拠に基づく推論です。**

ただし、残された疑問もあります。同じ opencode + Ollama（`qwen3.5:9b`）構成で、足軽4は3週間ほど安定稼働していたのに対し（少なくともハングの報告はありません）、足軽7は配備初日に2回連続でハングしました。この非対称の原因——両エージェント間の環境差（GPU メモリの状態、他プロセスとの競合等）——については、本記事では調査していません。

## 副産物の発見：Ollama の OpenAI 互換 API は冷たい

調査の過程で、思わぬ発見もありました。Ollama のコールド状態（モデル未ロード）での振る舞いです。

軍師が `curl` で直接テストしてみたところ：

**OpenAI 互換エンドポイント（`/v1/chat/completions`）:**
- 1回目: `timeout 30` → 30秒間、HTTP応答ヘッダすら一切受信されず
- 2回目: `timeout 100` → 100秒間、やはり無応答
- この間、`ollama ps` はモデル未ロード状態（コールド）が継続

**ネイティブエンドポイント（`/api/chat`）:**
- 同一モデル・同一プロンプトで約 **20 秒で完走**
  - ロード時間: 約 13.6 秒
  - 実生成: 残り約 6 秒
- 正常なストリーミング応答（実際の会話文）を返す

**コールド状態（モデル未ロード時）では、OpenAI互換エンドポイントは 2 回の別々の試行でそれぞれ無応答、ネイティブエンドポイントは 20秒で完走**という、顕著な非対称が実測されました。ウォーム状態（既にモデルがロード済み）での挙動は、本記事では未検証です。

opencode は内部で `@ai-sdk/openai-compatible` ドライバを使っており（ログの `llm.runtime=ai-sdk` で確認）、このエンドポイント側の挙動特性の影響を直接受けることになります。

## モデル側の制約も判明

さらに詳しく見ると、使っていたモデル（`qwen3.5:9b`）の実ロードサイズは **8.8GB** であるのに対し、GPU VRAM は **8GB** しかありません。（この数値は `ollama ps` コマンドの SIZE 列と PROCESSOR 列から取得しました。）

結果として、メモリ配置は：
- GPU: 72%（メモリ使用）
- CPU: 28%（メモリ使用）

という、**CPU と GPU にまたがる分割稼働** になっていました。

実際のタスク（system prompt や tool 定義を含む大きなプロンプト）を扱うとなれば、このメモリ制約下でのプロンプト評価に時間がかかり、**60秒のタイムアウト閾値に到達する確率が、単純な「hi」というプロンプトより格段に高い** と考えられます。

## 対応：すべて Claude に統一

ハングの実害（同日2回・計約6時間の停止）を受けて、**「Ollama は休眠温存し、全エージェントを Claude に統一する」** という判断を下しました。実は、本記事で紹介した調査の大半は、この判断を下したあとに行った事後検証です。

**修正可能な層と管理外の層**：
- **修正可能**：モデルのサイジング（例：7B Q4 への切り替え）、メモリ割り当ての最適化
- **管理外**：OpenAI互換エンドポイント側の非対称な挙動、opencode TUI 層のエラーハンドリング実装

未検証の改善策としては、VRAM 8GB に収まるより小さいモデル（例：7B Q4）への差し替えが考えられます。差し替えればメモリ制約下でのプロンプト評価遅延は改善し得たはずです。それでも検証せずに撤退したのは、管理外の層（互換 API の非対称な挙動、TUI 層のエラーハンドリング疑い）が依然として残り、サイジング修正だけでは信頼性要件を満たせないと判断したためです。

一方、**信頼性要件の視点**では、1体の足軽が障害に陥ると全体が停止します。Ollama を維持する便益は「Claude 枠の節約」ですが、軽量タスクを担う Haiku（Claude の軽量モデル）は Max プラン内で使えるため、この便益は実質ほぼゼロでした。他方、維持側には手動リセットや今回のようなハング調査といった障害対応コストが実際に積み上がっていました。切り替え自体は追加コストゼロで実行でき、可用性の向上が見込まれます。**維持の便益（ほぼゼロ）と維持の運用コスト（実測で発生）の比較として、撤退は合理的な判断**です。

## 再現性情報

以下は、当記事で報告した現象の再現に必要な環境仕様です。

**記事執筆時の環境（2026年6月～7月）：**
- **opencode**: 1.17.15
- **Ollama**: 0.24.0
- **モデル**: qwen3.5:9b（実ロードサイズ 8.8GB）
- **WSL2 カーネル**: 6.6.114.1-microsoft-standard-WSL2

**再現検証の際の確認ポイント：**

ハング時のモデル稼働状況を確認する場合、以下のコマンドで確認できます：
```bash
ollama ps
# NAME              ID              SIZE      PROCESSOR
# qwen3.5:9b        xxxxxxxx        8.8GB     72% GPU, 28% CPU
```

opencode 版の同種報告（TUI hang、timeout が画面に反映されない等）については、GitHub Issues で以下の日付時点で検索しました：
- opencode リポジトリ Issue 検索（2026年7月8日確認）
- キーワード: "TUI hang", "timeout", "unresponsive"
- 結果: 該当する公開報告なし

**設定追加の時系列：**

`opencode.jsonc` の timeout 設定は段階的に追加されたものではなく、以下の経緯で反映されています：
- **2026-06-17**: OpenRouter の無限空転防止策として `chunkTimeout` と `timeout` を新設
- **2026-07-08**: ローカル LLM（Ollama）向けに、OpenRouter の既存パターンを複製する形で追加

つまり、ローカル LLM 向けには、この 2026-07-08 の複製追加までの間、timeout 設定そのものが存在していませんでした。

## まとめ：「入れた」と「効く」は別問題

最大の教訓は、これです：

> 「タイムアウトを設定した」ことと「その設定が実際に効く経路を通っている」ことは、別の問題である

隔離テストでタイムアウトが正しく発動することを確認しても、実運用環境のすべての経路でそれが機能することを保証しません。特に opencode のような多層構造のツール（CLI ブリッジ → TUI ループ → LLM ドライバ → 外部 API）では、どの層でも「設定を読み込んだが、その効果を活かしきれていない」という齟齬が起きる可能性があります。

今回、最も疑わしいのは **opencode**（ブリッジ CLI）です。ただし、TUI 層の不備（エラーを画面に反映できないのか、タイムアウト自体が発火していないのか）が根本原因という見立ては、隔離環境での直接観測ではなく状況証拠に基づく推論です。ハングの直接原因（TUI画面が凍りつく挙動）を Ollama 単体では説明できませんが、互換 API の無応答特性とメモリ制約による遅延が、タイムアウト発火の頻度を押し上げた可能性は十分にあると考えています。
