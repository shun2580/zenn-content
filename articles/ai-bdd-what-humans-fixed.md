## はじめに

業務で、BDD（振る舞い駆動開発）を次の分担で作る進め方を試しています。チームで決めた仕様をもとに私がたたき台をつくり、AIにそれをシナリオなどのBDD形式で書き起こしてもらい、できあがったものを私がレビューする、という流れです。

この記事では、**AIが書き起こしたBDDに対して、人間（私）が何を指摘・修正したのか**をまとめます。指摘を記録して分類してみると、内容はおおむね4つの種類に収まりました。

結論を先に書くと、人間が直していたのは文章の誤りではなく、「**AIが広げ、人間が絞る**」ための判断でした。

本記事では、BDDを書き上げるまでを扱います。関係者との認識合わせや実装は、まだこれからの段階です。

:::message
私の役割は、仕様のたたき台づくり、AIが書き起こしたBDDのレビュー、指摘の記録です。
手戻りが減ったかどうかの成果はまだ出ていません。本記事は「やってみて分かったこと」の途中報告です。
:::

## 背景：「要望と違う」で起きる手戻り

私たちは受託開発で、次のような流れで仕事を進めています。

```
クライアントの要望 → ディレクター → エンジニア → ステージングでクライアントが確認
```

この流れで、ステージングを確認したクライアントから「要望と違う」と言われ、手戻りが起きることがありました。原因の多くは、要望が人を経由して伝わる間に解釈が少しずつずれ、三者がそれぞれ別の認識のまま進んでしまうことでした。

そこで、**BDDの自然言語による「ふるまいの記述」を、クライアント・ディレクター・エンジニアの三者が認識を合わせる基準にする**進め方を、課内で試すことになりました。

## 進め方

今回の進め方は次のとおりです。

1. チームで仕様を決め、私がたたき台にまとめる
2. たたき台をAIに渡し、仕様として整形する。不足している点や詳細も追加してもらう
3. GitHub Copilotで仕様をGherkin形式に変換する
4. 私がレビューし、誤りや不足を追記する

私が担当した機能のBDDは、すでに作成を終えています。

ただ、Gherkinは非エンジニアには読みにくいという問題があります。そのため関係者への説明には、各メンバーのBDDを**正本**にして作成した、非エンジニア向けの説明資料を使いました。

## 指摘を記録するときのルール

レビューの途中から、AIへの指摘や修正指示を記録に残すようにしました。あとで振り返り、AIがどこで間違えやすいかを知るためです。

記録には、1つだけルールを設けました。

> **AIが提案しただけの内容を、自分の指摘として扱わない。**

AIと対話しながら仕様を詰めると、AIの提案に私が「それでいいです」と答えるだけの場面がよくあります。このとき、細かい仕様まで自分が指示したかのように記録すると、誰が何を判断したのかが分からなくなります。

そこで、次のように分けて記録しました。

- 自分が明示的に指摘・指示したこと
- AIが提案し、自分が採用を判断したこと
- AIが提案しただけで、まだ合意していないこと

このルールのおかげで、「人間が直した内容」だけを取り出して分析できました。

## 指摘を分類すると4つに収まった

記録した発言は、複数のチャットの分を合わせて約110件でした。内訳は、AIの出力や前提を正した「指摘」が約36件、作業や確認を求めた「依頼」が約52件、仕様判断や情報提供が約21件です（記録表の行数と発言数を数えた目安です）。

このうち「指摘」を分類すると、次の4つにまとまりました。4つに当てはまらない指摘（資料の取り違えの訂正など）が約4件ありました。

| 分類 | 内容 | 指摘の件数 |
| --- | --- | --- |
| ① 対象範囲・運用の判断 | どんな場面で使う機能なのか、どこまでを扱うのか | 約14件 |
| ② 根拠の確認 | API仕様やDB定義を実際に確認したか | 1件 |
| ③ チーム内の一貫性 | 他のメンバーが書いたBDDや共通部分と書き方が揃っているか | 約7件 |
| ④ 確定事項と仮案の区別 | 決まったことと、相談中の案を混ぜていないか | 約10件 |

②は「指摘」としては1件ですが、仕様書や定義の確認を求めるやり取りは「依頼」として繰り返し出てきました。件数以上に、仕様の中身を左右した分類です。

それぞれ、具体的に見ていきます。

:::message
以降の例は、特定を避けるために機能の中身を一般化・加工していますが、指摘の構造（AIが何をし、人間が何を直したか）は変えていません。
:::

### ① 対象範囲・運用の判断

最も多かったのがこの種類の指摘で、指摘全体の約4割（36件中14件）を占めました。

AIは、起こりうるケースを網羅しようとします。それ自体は長所ですが、**実際の運用では起きない場面や、担当範囲の外まで仕様を広げてしまう**ことがありました。

例えば次のようなものです。

- **一度しか使わない処理を、通常運用でも使う前提で書いてしまう**
  リリース準備のときに一度だけ使う一括取込を、日常の運用でも使うかのように書いたり、通常の処理との併用について何度も確認してきたりしました。
- **例外対応のために、専用の機能や手順を増やしてしまう**
  ある種類の失敗が起きたときのために、AIは追加の再取得手順を提案してきました。しかし実際の運用では、連携先に確認すれば済む話です。手順を増やすと運用が面倒になるため、追加しないよう指摘しました。
- **判定の条件を広げすぎる**
  公開してよいかの判定に、過去の実行履歴まで含めようとしていました。「今回の処理の結果だけで判断すればよい」と伝えました。
- **別の機能の話を持ち込む**
  別の画面の仕様や、別の担当者が書くバッチの本体仕様まで検討対象に入れていました。関連する部分は扱いつつ、担当範囲の外は外すよう指摘しました。

これらをBefore/Afterで比べると、次のようになります。

| 例 | AIの出力（Before） | 私の指摘 | 修正後（After） |
| --- | --- | --- | --- |
| 一度きりの処理 | 一括取込と通常の取込を併用した場合の挙動を、シナリオや質問として何度も提示 | 「これは一回しか使わない」 | 併用の考慮を外し、一括取込を一度きりの処理として記述 |
| 例外対応 | 失敗時のために、専用の再取得手順をシナリオとして追加 | 「連携先に確認すれば済む」 | 再取得手順を追加せず、失敗は検知するだけにとどめる |
| 判定条件 | 公開可否の判定に、過去の実行履歴を含める | 「今回の処理の結果だけで判断すればよい」 | 今回の処理結果のみを判定に使う |

**どの場面で使い、どこまでを扱うのか**という判断は、業務と運用を知っている人間にしかできません。上の例のように、AIに任せると、起こりうるケースを広く拾おうとして機能が増える方向に進みやすい、というのが今回の私の実感です。

### ② 根拠（API仕様・DB定義）の確認

AIは、もっともらしい仮定を置いて仕様を書いたり、仮定をもとに質問してきたりします。

例えば、必須項目やnullの扱いを、API仕様書やテーブル定義を見ずに決めようとしていました。そこで「APIドキュメントとマイグレーションを実際に見比べて確認してほしい」と依頼しました。

根拠を確認しながら仕様を詰めていくと、次のような点が出てきました。

- 連携データで、**項目自体が存在しない場合**と、**値として明示的にnullが来た場合**を区別する必要があった（更新時に既存値を保持するのか、クリアするのかという扱いが変わるため）。項目が存在しない場合に既存値を保持する、という扱いは私から指定しました
- IDとして受け付ける値の範囲は、DBの定義を根拠に決める必要があった
- DB上はnullを許容しているのに、既存の管理画面では入力必須になっている項目があった

最後の例は、データを取り込めるかどうかだけを見ていると気づきません。**取り込んだ後に、既存の画面で編集できるか**まで考える必要があります。これはディレクターに相談する事項として残しました。

仮定のまま質問されると、人間は毎回「本当はどうなっているか」を自分で調べて答えることになります。**先に根拠を確認してから質問してもらう**と、やり取りの回数が減ると感じました。

Before/Afterをシナリオで示すと、次のようなイメージです（項目名や振る舞いは加工しています）。

| | 内容 |
| --- | --- |
| AIの出力（Before） | 仕様書もテーブル定義も見ずに、「項目が空なら空で更新する」と仮定してシナリオ化 |
| 私の指摘 | 「APIドキュメントとマイグレーションを実際に見比べて確認してほしい」と依頼したうえで、「項目自体が存在しない場合は既存値を保持する」と指定 |
| 修正後（After） | 「項目が存在しない」と「明示的にnull」を別のシナリオに分ける |

**Before**

```gherkin
Scenario: 説明文が空で連携された場合
  When 説明文が空のデータが連携される
  Then 説明文は空で更新される
```

**After**

```gherkin
Scenario: 説明文の項目が連携データに存在しない場合
  When 説明文の項目を含まないデータが連携される
  Then 説明文は更新されず、既存の値が保持される

Scenario: 説明文が明示的にnullで連携された場合
  When 説明文のnullを含むデータが連携される
  Then 説明文はクリアされる
```

「空」という曖昧な言葉が、実は二つの別々の状態を指していたという例です。

### ③ チーム内の一貫性

今回は、チームのメンバーがそれぞれ別の機能のBDDを担当しています。そして、機能同士には共通する部分があります。

ところが、AIは目の前のBDDだけを見て最適な方式を考えます。その結果、**非同期処理や通知、実行状態の管理などを、他のメンバーのBDDとは別の方式で設計してしまいました。**

途中でこのずれに気づき、次のように方針を切り替えました。

> 他メンバーが書いたBDDの書き方を参考に修正してほしいです。
> また、非同期処理と通知は同じ形にしてほしいです。
> 他にも共有している部分は、そちらを優先にしてほしいです。

| | 内容 |
| --- | --- |
| AIの出力（Before） | 非同期処理や通知、実行状態の管理を、自分のBDDだけを見て独自の方式で記述 |
| 私の指摘 | 上記の発言 |
| 修正後（After） | 他メンバーのBDDの書き方に揃え、共有部分はそちらの形を優先 |

AIが提案していた方式が、それだけを見れば悪いわけではありません。しかし、同じシステムの中で同じことを違う方法で実現すると、実装も保守も大変になります。**「この機能にとっての最適」より「チームとしての一貫性」を優先する**という判断は、人間が明示しないとAIは選びませんでした。

また、共有している部分については、別の担当者と一緒に検討する必要があります。相手の機能の内部仕様を、自分の担当側だけで決めてしまわないよう注意しました。

### ④ 確定事項と仮案の区別

AIとの対話で仕様を詰めていくと、文書の中に「決まったこと」と「まだ相談中のこと」が混ざっていきます。この区別が崩れることが何度もありました。崩れ方は2方向あります。

**回答済みの内容が、未決事項に残り続ける**

質問に答えても、文書の「未確定・相談事項」の欄がなかなか減りませんでした。回答した内容が本文やシナリオに反映されず、未決欄に残ったままになったり、同じ論点をまた質問されたりしたためです。

このとき伝えたのは次のことです。

> 確認事項はまとめてお願いします。
> 小分けにしているため一向に確認事項が減っていません。

| | 内容 |
| --- | --- |
| AIの出力 | 回答済みの内容が未確定欄に残ったまま、新しい質問が1つずつ追加される |
| 私の指摘 | 上記の発言 |
| 修正後 | 関連する論点をまとめて確認し、回答済みは本文・シナリオへ移して未確定欄から外す |

質問が小出しにされると、回答するたびに新しい質問が出てきて、終わりが見えなくなります。関連する論点はまとめて確認してもらい、回答したものは未決欄から外して仕様に移すように依頼しました。

**仮案が、確定した仕様のように書かれる**

逆方向のずれもありました。私が「一旦これで」と置いた暫定値や、他のメンバーに相談するための仮案が、確定仕様として書かれることがあったのです。

相談用の案を勝手に確定させると、相談する機会そのものが失われます。暫定値には暫定であることを明記し、未確定の欄に置くよう指摘しました。

**今どの段階なのか**

似た話として、作業の段階の取り違えもありました。AIが「実装側のファイルが未更新です」と、残作業のように報告し続けたことがあります。しかし今はまだ、実装前のBDDを作っている段階です。実装側への反映は後の工程なので、今の完了条件には入りません。

**何が決まっていて、何が決まっていないのか、そして今どの段階なのか。** この状態を管理するのは、最後まで人間の役割でした。

## AIに任せられたこと

ここまで指摘の話ばかり書いてきましたが、AIに任せてうまくいった部分も多くあります。主に次の3つです。

- **記述**：私が考えた仕様のたたき台を、Gherkinのシナリオに書き起こす
- **網羅**：正常系だけでなく、失敗時や境界値などのシナリオを洗い出す
- **整形**：BDD全体の形式を揃える。BDDの変更を説明資料に反映する

特に網羅については、人間が見落としていたケースをAIが挙げてくれた場面もありました。そして、AIが網羅的に書き出してくれるからこそ、「このケースは運用上起きないから外す」という判断（①）ができた面もあります。

つまり、**AIが広げ、人間が絞る**という役割分担になっていました。

## 振り返り

指摘を4つに分類して見えてきたのは、人間が直していたのは文章の誤りではなく、**判断が必要な部分**だったということです。

| AIが得意だったこと | 人間が担ったこと |
| --- | --- |
| 仕様のたたき台をシナリオとして書き起こす | どの場面で使い、どこまで扱うかを決める |
| ケースを漏れなく洗い出す | 根拠となる仕様・定義を確認させる |
| 形式を揃え、変更を反映する | チームとしての一貫性を保つ |
| | 決まったことと仮案の状態を管理する |

逆に言えば、この4点を最初からAIへの指示に含めておけば、指摘の回数は減らせるかもしれません。例えば次のような指示です。

- 想定する運用と担当範囲を、最初に明示する
- 仕様や定義が手元にあれば、仮定を置く前に必ず確認させる
- 他のメンバーの成果物と共通する部分は、既存の書き方を優先させる
- 回答済みの論点は未決欄から外し、仮案には仮案であることを明記させる

## おわりに

現時点で、各メンバーのBDDをもとに説明資料を作成し、関係者に共有しました。いまは、フィードバックを受けている段階です。

このあとは、フィードバックをBDDに反映して三者の認識を合わせ、実装に進む予定です。その中で、次の点を確かめていきたいと考えています。

- BDDが、本当に認識合わせの基準として機能するか
- 振り返りで挙げた4点を最初から指示に含めると、指摘が実際に減るか

AIにBDDを書かせる場面では、書かせることより「何を直すか」を決めるほうに人間の時間が使われていました。同じようにAIで仕様を書いている方の参考になれば幸いです。
