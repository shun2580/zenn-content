> 本記事はAIエージェント（Claude / 自作マルチエージェント環境）との対話を通じて設計・実装した内容を、筆者が再構成したものです。AI協働・AI校正の利用を開示します。記載した数値・仕様は2026年7月時点のもので、末尾に一次情報リンクをまとめています。

## 発端：Sonnet 5 を手で切り替えたときの面倒くささ

きっかけは Claude Sonnet 5 のリリースでした。将軍・家老・足軽からなる階層型マルチエージェント環境（[前回記事](https://zenn.dev/masafumi_heijo/articles/791fbea6eddd68)）では、各エージェントのモデルを `config/settings.yaml` で管理しています。Sonnet 5 が出たのを知って、それまで Sonnet 4.6 を指定していた箇所を手で書き換えました。

書き換え自体は一度で済む作業です。ただ、そのとき「これを新版が出るたびに毎回やるのか」と面倒に感じました。

- 新版が出たことに気づくのが遅れる（自分でドキュメントを見に行かないと分からない）
- 気づいても「本当に切り替えて大丈夫か」の確認は結局手作業
- エージェントの数だけ、この手間が積み重なる

「気づいたら自動で切り替わってほしい」——最初はそう考えました。しかし検討を進めるうちに、**全自動適用はそれ自体が事故のもとになる**と分かり、方針を転換しました。

## 全自動アップデートは事故る——リスク棚卸し

「新版が出たら即・自動で `settings.yaml` を書き換えて反映する」という設計を検討した際に洗い出したリスクは次の通りです。

| リスク | 内容 |
|---|---|
| 破壊的変更・挙動変化 | モデル版によって対応機能・挙動が変わりうる。切り替え直後にエージェントが想定外の挙動をする可能性がある。**実例**（Sonnet 4.6→Sonnet 5、公式ドキュメント確認済み）: (1) Extended thinkingが非対応化（Sonnet 4.6は対応、Sonnet 5は非対応）、(2) 新トークナイザー採用により同一テキストのトークン数が約30%増加（Sonnet 4.6以前は旧トークナイザー）。個別モデルの機能対応・挙動差の網羅的検証は本記事の範囲外とし、切替前に各自が公式ドキュメントで確認すべき項目として挙げる。なお、本システム（`config/settings.yaml`）を確認したところ、現時点でmanualなextended thinkingの明示的な有効化や、temperature／top_p／top_kといった非デフォルトsampling parameterの設定を行っているエージェントは存在しない（将軍〜足軽7号まで全て未設定）。そのためこれは本システムで実際に発生した事故ではないが、こうしたパラメータを明示的に使う構成では、非対応モデルへの切り替え後にAPIリクエストがエラーとなり処理が止まりうる点には変わらず注意が必要である |
| コスト暴発 | 新版の単価や導入価格（intro pricing）の条件を確認せずに切り替えると、想定外の課金増につながりうる。**実例**: Sonnet 5は導入価格（入力$2／出力$10、1MTokあたり）が2026年8月31日まで適用され、2026年9月1日からは標準価格（入力$3／出力$15、Sonnet 4.6と同額）に切り替わる。期限を把握せず運用を続けると、切替日をまたいだ時点で想定外のコスト変動が生じる。また、標準単価がSonnet 4.6と同額（据え置き）であっても、新トークナイザー採用によるトークン数約30%増の影響で、同じ処理をさせた場合の実コストは最大3〜4割増になりうる——「単価据え置き＝コスト変わらない」ではない点に注意が必要である |
| ティア誤爆 | Haiku→Sonnetのような**ファミリー跨ぎ**の誤爆で、意図しない上位モデルに切り替わってしまう |
| 未提供IDで起動失敗 | 案内されたIDがまだ全アカウントに展開されていない等の理由で起動に失敗する |
| スクレイピング経由のインジェクション | 検知処理がWebページの内容をLLMに解釈させる設計だと、ページ内の悪意ある文字列がプロンプトインジェクションの経路になりうる |
| セッション強制リセット乱発 | 自動切り替えのたびに稼働中エージェントのセッションを切ると、作業中の文脈が失われる |

これらはどれも「気づいたら自動で最新化されている」という体験の裏側で発生しうるコストです。**検知（気づくこと）と適用（切り替えること）を同じ処理に混ぜると、リスクも一緒に自動化してしまう**、というのが検討の結論でした。

## 設計原則：検知と適用の分離（notify-only）

そこで採用したのが、**「検知は自動、適用は人間の承認を経て人間が実行する」**という分離です。

- 新モデル版が出たかどうかは、決定論的なスクリプトが定期的に（起動時に）確認する
- 見つかったら通知するだけ。`settings.yaml` の書き換えや実際の切り替えコマンド実行は一切しない
- 切り替えるかどうか、いつ切り替えるかは、通知を受けた人間が判断する

この仕組みが `scripts/model_update_check.py` です。

## 検知器の実装勘所

### LLMを介さない決定論スクリプト

検知処理はPythonの正規表現ベースで完結しており、LLMにWebページの内容を解釈させる工程がありません。これにより、ページ内容が悪意あるものだったとしても、それがエージェントへの指示として実行される経路（プロンプトインジェクション）を作らずに済みます。

### 情報源は第一者公式ドキュメントの.md固定

情報源はハードコードされた1つのURL（Anthropic公式ドキュメントの `overview.md`）のみです。任意のURLを踏みに行くことはありません。

### 脚注汚染の罠

公式ドキュメントの表には、Bedrock/Google Cloud列などに脚注番号が付与されている箇所があります。単純な文字列抽出だと、モデルIDと脚注番号がくっついた文字列（例: モデルID末尾+脚注番号）を誤ってバージョン番号として解釈してしまう恐れがあります。`model_update_check.py` では「`Claude API (ID|alias)` を含む行だけ」から抽出したうえで、日付サフィックスや `-vN` を除去し、`^claude-(family)-(major)(?:-(minor))?$` という厳格な正規表現で検証することで、この誤認識を防いでいます。

### 同ティア限定／fixed:trueはスキップ／重複通知抑制

- 比較は同じファミリー（例: sonnet同士）内でのみ行い、ファミリー跨ぎの提案はしない
- `settings.yaml` 側で `fixed: true` を付けたエージェントは検知対象から除外される
- 一度通知した候補は state ファイル（`logs/model_update_check.state.json`）に記録し、同じ組み合わせを再通知しない

## 起動時トリガ：PCを常時起動しない前提での工夫

このマルチエージェント環境はPCを常時起動しているわけではないため、cronの定時実行はそのままでは機能しません（PCが起きていない時間帯は実行されない）。かといって毎回のシェル起動で無条件に検知処理を走らせるのも重すぎます。

そこで `~/.bashrc` に、**ブートごとに一度きり**実行されるガードを追加しました。

- `/proc/sys/kernel/random/boot_id` を比較し、前回実行時と同じブートなら何もしない（取得できない環境では `/proc/uptime` から近似したブートエポックにフォールバック）
- 対話シェル（`$-` に `i` が含まれる場合）でのみ動作させ、非対話シェルやスクリプト実行を邪魔しない
- `nohup ... &` + `disown` でバックグラウンド実行し、シェルの起動をブロックしない
- 万一失敗しても `|| true` でシェルの起動自体は壊さない

`sudo` や `/etc/wsl.conf` の変更は避けています。システム全体の設定に手を入れるのは影響範囲が大きく、今回の目的（起動時に一度だけ軽い検知処理を挟む）に対してはリスクが見合わないと判断したためです。

## これをマルチエージェントで作った話

この仕組み自体、将軍→家老→足軽→軍師QCという普段のワークフローに乗せて作りました。将軍が方針（検知・通知のみ、適用は人間承認）を決め、家老がタスクに分解し、足軽が実装、軍師が品質チェックする——という一連の流れです。この体制についての詳細は[1本目の記事](https://zenn.dev/masafumi_heijo/articles/791fbea6eddd68)を参照してください。

## 現状：まだ「初めての新版」を待っている段階

正直に書いておくと、この検知器は Sonnet 5 を**手で切り替えた後**に「次からは楽をしたい」と思って整備したものです。つまり、実運用で新版を検知して通知を出した実績は、この記事を書いている時点ではまだありません。次に Anthropic が新しいモデル版を出したときが、この仕組みにとって初めての実戦になります。

現時点で確認できているのは、既知のモデル一覧を入力として与えたときに、検知ロジックが意図通りに振る舞うか——同じファミリー内の新版だけを候補として拾い、`fixed: true` のエージェントを除外し、一度通知した組み合わせを再通知しないか——というロジックの動作までです。「実際の新版リリースで正しく発火するか」は、次の機会に検証することになります。

## 教訓：『適用しない』設計の価値

自動化を検討する際、つい「全部自動でやってくれる」ことをゴールにしがちです。しかし今回のケースでは、**危険な最後の一歩（実際にモデルを切り替える操作）だけを意図的に人間に残す**ことが、最も安全で納得感のある設計でした。

- 検知：頻度が高く、間違えても実害が小さい → 自動化する価値が高い
- 適用：頻度が低く、間違えると実害が大きい（コスト・挙動変化） → 人間の判断を残す価値が高い

「どこまで自動化するか」ではなく、「どこを自動化“しない”ままにするか」を先に決める、という順番の方が今回はうまくいきました。

## まとめ

モデルの更新追随は、検知と適用を分けることで、利便性と安全性を両立できます。

- 追随（気づくこと）は自動化してよい。ただし決定論的で、任意コンテンツを解釈させない設計にする
- 適用（切り替えること）は自動化しない。通知を受けた人間が、価格・破壊的変更を確認したうえで実行する

「追随は自動、決断は人間」——この線引きが、今回の一番の収穫でした。
