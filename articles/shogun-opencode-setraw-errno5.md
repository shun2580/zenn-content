## 音で気づいた

きっかけは音でした。

作業をしていたら、システムの通知音が妙にしつこく鳴る。一回二回ならともかく、何度も繰り返し鳴り続けるので、さすがに「何かおかしいな」と思って tmux を覗きました。すると、あるエージェントのペインに、わけのわからない文字列が延々と流れ続けている。

これが今回の調査の出発点です。最終的には `setRawMode failed with errno: 5` という、ちょっととっつきにくいエラーまでたどり着くのですが、結論を先に言ってしまうと、犯人は「遅いローカルLLM」と「その遅さを異常だと勘違いした監視スクリプト」の組み合わせでした。

なお、舞台にしているのは複数のAI CLIを tmux 上で並列に動かす [multi-agent-shogun](https://github.com/yohey-w/multi-agent-shogun)（yohey-w さんのプロジェクト）です。私はこれをforkして使っていて、以下はその上での実体験になります。

## 前提：エージェントを「外から」叩いて起こす仕組み

本題に入る前に、最低限の構成だけ説明させてください。

このシステムでは、エージェントが tmux のペインに1体ずつ常駐しています。連絡はファイルベースのメールボックスでやり取りするのですが、「メッセージ届いたよ」と相手を起こす部分だけは tmux 経由です。`inbox_watcher.sh` が `inotifywait` でファイルの変更を見張っていて、変化があると `tmux send-keys` で `inbox3`（未読3件、の意）みたいな短い合図をペインに送り込みます。

そして、合図を送っても反応がないと、watcher は段階的にしつこくしていきます。もう一度起こす、Escape を送る、最終的には `/clear` 相当のリセットをかける、という具合です。

ここで頭の片隅に置いておいてほしいのが、この仕組みは結局のところ、エージェントの外側からキー入力を注入して操縦しているという点です。あとでここが効いてきます。

## 現場検証：ペインがシェルに落ちていた

問題のペインを `capture-pane` で覗くと、こんな状態でした。

```
35;18;7M35;17;7M35;17;6M35;16;6M35;16;5M35;15;5M...
```

座標っぽい数字と `M` がひたすら続いている。最初は完全に文字化けかと思ったのですが、これは xterm のマウストラッキング（SGRマウスモード）が吐くエスケープ列です。TUIがマウス追跡モードをONにしたまま死んでしまい、そのあとの端末がマウスの動きを生のテキストとして垂れ流していた、というのが正体でした。

ついでに言うと、発端だった鳴り止まない通知音も、たぶんこの垂れ流しに紛れていた端末ベル（制御文字）が繰り返し鳴っていただけだと思います。つまり、画面で起きていた異常が、たまたま耳にも届いていた、というオチでした。

次に、各ペインのフォアグラウンドプロセスを見てみます。

```bash
tmux list-panes -a -F '#{pane_index} #{@agent_id} cmd=#{pane_current_command}'
# ...
# 4 ashigaru4 cmd=bash   ← これだけTUIが死んでいる
```

他のエージェントは `claude` や `node` を動かしているのに、問題の子（足軽4）だけ `bash` になっている。OpenCode の TUI が落ちて、素のシェルに戻ってしまっていたわけです。

ちなみにこの足軽4、コスト削減のためにローカルLLM（Ollama の `qwen3.5:9b`）を OpenCode 経由で動かしているエージェントでした。この「ローカルLLM」というのが伏線です。

そして地味に重要なのが、マウスモードが残っていたこと。もし TUI が `/exit` などで行儀よく終わっていれば、終了時にマウスモードを戻すエスケープを送って、端末を元の状態に片付けてから去るはずです。それが残っているということは、片付ける暇もなく落ちた＝行儀の悪い死に方をした、という見立てになります。

## ログは、きれいに途切れていた

OpenCode のログ（`~/.local/share/opencode/log/`）を追います。起動まわりはいたって普通でした。

```
INFO service=db   ... applying migrations
INFO service=config ... loading
INFO service=provider providerID=ollama found
INFO service=skill count=3 init
（ここで途切れる）
```

エラーもシャットダウンログも残さず、本当にぶつっと終わっている。しかも複数セッションのログを見比べると、死ぬタイミングがバラバラでした。起動直後のものもあれば、1時間近く動いてから死んだものもある。特定の処理で必ずコケる、という感じではなさそうです。

このあたりで「メモリかな」とも疑いました。9Bモデルなので、ロード時に一気にメモリを食ってOOMで殺された可能性はある。でも、

- `dmesg` に OOM Killer の痕跡がない
- システムRAM（合計約15GB）には十分な空きがあった（モデル自体は約6.6GB）

ということで、メモリ枯渇の線は消しました。後で出てくる errno5 も、メモリではなく端末のI/Oエラーなので、ここは筋が通っています。

## 決定的な一行

手詰まりかと思いつつ、過去のクラッシュログまで含めて横断で grep してみたら、これが出てきました。

```
ERROR service=default e=setRawMode failed with errno: 5  exception
ERROR service=default error=setRawMode failed with errno: 5  process error
```

`setRawMode` は、TUIが端末をrawモードにするための呼び出しです。1文字打つたびに即座に反応するために、行バッファリングやエコーをOFFにする、TUIにとっては心臓みたいな処理ですね。

問題は `errno: 5`、つまり EIO（Input/output error）。これが拾われないまま「process error」として、OpenCode をそのまま落としていました。

で、`setRawMode` が EIO で落ちるのはどういうときか。経験的には、PTY（疑似端末）の状態が外から乱されたときが多い。……ここで、さっき頭の片隅に置いてもらった「外側から tmux send-keys でキーを叩いている」が効いてきます。

## つながった

集めた材料を並べると、最も筋の通る仮説はこういう流れです。

```
① ローカルLLM qwen3.5:9b の応答が遅い（実測で150〜300秒かかっていた）
        ↓
② watcher の「無応答」判定は、秒で返るクラウドLLMを前提に
   120秒/240秒で組まれていた → ちゃんと推論中なのに「無応答」と誤判定
        ↓
③ watcher が tmux send-keys で nudge・Enter・/new を連打
   ── TUIが描画や推論をしている真っ最中にもキーを突っ込む
        ↓
④ そのキー注入がTUIの端末モード操作とぶつかる（仮説）
   → setRawMode が errno5(EIO) で失敗
        ↓
⑤ TUI が process error で即死。/exit を通らないので
   マウス追跡モードが残ったまま → シェルにエスケープ列が垂れ流し
```

要するに、悪かったのは遅いローカルLLMそのものではなく、その遅さを「異常」とみなして外からキーを叩き続けた監視ロジックのほうでした。クラウドLLMなら数秒で返るので一生表面化しなかった閾値が、ローカルLLMに変えた途端に牙を剥いた、という話です。

正直、最初は完全にOpenCodeかOllamaのバグを疑っていたので、自分のところの監視スクリプトが原因だったとわかったときは、ちょっとバツが悪かったです。

## 直した

モデルはコスト削減のために `qwen3.5:9b` のまま据え置きたい。その前提で、対策を2つ入れました。

### 対策A：CLIごとに無応答の閾値を変える

「遅いだけで、ちゃんと動いている」状態を無応答と取り違えないように、OpenCode系だけ閾値をぐっと伸ばします。

```bash
# 従来（クラウドLLM前提）
ESCALATE_PHASE1=${ESCALATE_PHASE1:-120}   # 2分
ESCALATE_PHASE2=${ESCALATE_PHASE2:-240}   # 4分

# OpenCode/ローカルLLM 向けに延長
ESCALATE_PHASE1_OPENCODE=${ESCALATE_PHASE1_OPENCODE:-600}   # 10分
ESCALATE_PHASE2_OPENCODE=${ESCALATE_PHASE2_OPENCODE:-900}   # 15分
```

閾値の根拠：実測の応答時間が150〜300秒だったため、誤検知を避けるため最大実測値の2〜3倍（600秒・900秒）を安全マージンとして設定した。

エスカレーション判定のところで、そのエージェントが今どのCLIで動いているかを見て、閾値を差し替えます。

```bash
local phase1=$ESCALATE_PHASE1
local phase2=$ESCALATE_PHASE2
if [[ "$(get_effective_cli_type)" == "opencode" ]]; then
    phase1=${ESCALATE_PHASE1_OPENCODE:-600}
    phase2=${ESCALATE_PHASE2_OPENCODE:-900}
fi
```

ついでに、起こし直し（nudge）の間引き間隔も OpenCode は長め（60秒→300秒）にしました。推論中にキーを連打する機会そのものを減らせば、そもそもの衝突が起きにくくなる、という狙いです。これが今回の根っこの対処になります。

### 対策B：落ちたら勝手に起き上がる番犬

とはいえ、閾値を伸ばしても絶対に落ちないとは言い切れません。なので、落ちたときに自分で復活する仕掛けも足しておきました。「ペインが素のシェルに戻っている＝TUIが死んでいる」と見て、自動で再起動します。

```bash
check_and_heal_dead_cli() {
    [ "${ASW_AUTO_HEAL:-1}" = "1" ] || return 0

    local pane_cmd
    pane_cmd=$(tmux display-message -t "$PANE_TARGET" -p '#{pane_current_command}' 2>/dev/null)

    case "$pane_cmd" in
        bash|sh|zsh|fish|-bash|-sh|-zsh)
            DEAD_CLI_STREAK=$((DEAD_CLI_STREAK + 1)) ;;
        *)
            DEAD_CLI_STREAK=0; return 0 ;;
    esac

    # 2回連続で「シェル」を見たときだけ復旧（起動直後の一瞬を誤検知しない）
    [ "$DEAD_CLI_STREAK" -ge 2 ] || return 0
    # クールダウン中なら何もしない（再起動の連打防止）
    # ...
    bash "${SCRIPT_DIR}/scripts/switch_cli.sh" "$AGENT_ID"
}
```

ここで気をつけたのは誤検知です。正常な再起動の最中も、一瞬だけペインはシェルに戻ります。それを「死んだ！」と勘違いして再起動をかけたら、今度は再起動ループになりかねない。なので、

- シェル状態を2回連続で見てから動く（一瞬の復帰では動かない）
- クールダウンを挟んで連打を防ぐ
- `ASW_AUTO_HEAL=0` でいつでも止められる

という安全側の作りにしてあります。

## 振り返って思ったこと

### 外からキーを叩いてTUIを操るのは、思ったより繊細

`tmux send-keys` でTUIを自動操縦するのは手軽だし強力なのですが、相手が端末モードをいじっている最中に横から入力をねじ込むと、こうやって `setRawMode` あたりが EIO で落ちることがある。便利さに甘えて「相手が今キーを受け取れる状態か」をまったく気にしていなかったのが、今回の反省点です。

### クラウド前提のタイムアウトは、ローカルLLMで簡単に壊れる

「無応答」と判断する閾値は、応答速度の前提とワンセットだったんだな、と改めて思いました。秒で返ってくるクラウドLLM用の数字を、分で返ってくるローカルLLMにそのまま使うと、正常な動作を異常と見なして暴れ出す。ローカルLLMでコストを下げる人はこれから増えると思うので、監視やタイムアウトの値は「モデルの速度感」ごとに分けて持っておくのが無難です。

### きれいに途切れているログは、それ自体が手がかり

エラーも残さずぶつっと終わっているログと、端末に残ったマウスのエスケープ列。この2つが「行儀よく終わっていない」と教えてくれていました。そこに `dmesg` でOOMを除外できたことが乗って、ようやく「プロセスレベルの端末I/Oエラーだ」と当たりをつけられた。何も出ていないことが、逆にヒントになることもあるんだなと。

## おわりに

ローカルLLMは安くてありがたいのですが、「遅い」という性質は、その周りのインフラ（監視・タイムアウト・自動操縦）の前提をこっそり崩していきます。今回も、`setRawMode errno5` という見た目はいかついエラーが、ほどいてみれば「遅さ × かまいすぎ」というわりと素朴な話でした。

tmux × AI CLI で似たような自動化をやっている方が、同じ罠を踏んだときの手がかりになれば幸いです。
